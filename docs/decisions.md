# 設計判断の記録

採用した案だけでなく、**採らなかった案とその理由**、および**判断が変わる条件**を残す。

---

## 1. 在庫を「台帳 + キャッシュ」で持つ

**決定**: `stock_movements`（追記専用の増減台帳）を真実とし、`products.stock_quantity` は同一トランザクションで更新する集計キャッシュとする。

**採らなかった案**

- _`products.stock_quantity` だけを持つ_ — 最も単純だが、在庫が合わないときに原因を追えない。棚卸で差異が出ても、いつ何が起きたのか分からない。
- _台帳のみを持ち、現在庫は毎回 SUM で計算する_ — キャッシュのずれは原理的に起きないが、商品一覧のたびに全商品の集計が走る。表示が最も頻繁な操作なので割に合わない。

**理由**: 業務システムでは「現在の値」より「なぜその値になったか」が重要になる場面が多い。誤操作の追跡、棚卸の突合、そして Phase 4 の発注推奨（販売ペースの算出）が、すべて同じ1枚の台帳に乗る。

**代償**: 書き込み量が増え、キャッシュとの整合を保つ責任が生まれる。後者は `verify_stock_integrity()` で検査可能にし、そもそもずれないよう RLS と列単位 GRANT で書き込み経路を1つに絞ることで対処した。

---

## 2. 在庫の引き当ては「注文受付時」

**決定**: 注文を作成した時点で在庫を引く。キャンセル時に戻す。

**採らなかった案**

- _発送時に引く_ — 在庫の減少と実際の出庫が一致するので帳簿上は素直。しかし受付から発送までの間、在庫は「まだある」ことになり、その間に入った注文が売り越しになる。
- _引当数を別カラムで持つ（論理在庫 / 物理在庫の分離）_ — 正確だが、小規模ECにこの複雑さは過剰。Phase 1 で導入すると、扱う概念が倍になる割に得るものが少ない。

**理由**: 小規模ECで金銭的・信用的な損失が最も大きいのは売り越し。「在庫があると表示して受注したのに出荷できない」は、謝罪と返金と再発防止の運用コストを伴う。

**判断が変わる条件**: 予約販売やバックオーダーを扱うようになったら、論理在庫と物理在庫の分離が必要になる。

---

## 3. 発送済みからキャンセルできない

**決定**: 遷移規則から `shipped → cancelled` を除く。

**理由**: 発送後の取り消しは「返品」であり、在庫の戻し方が違う。返品は商品が手元に戻り、検品を経てから在庫に戻すもので、キャンセルのような即時の戻しをすると、実際には存在しない在庫が販売可能になる。

同じ「在庫を戻す」でも業務が別物なので、同じ遷移として扱わない。返品フローは Phase 4 で別に設ける。

---

## 4. 業務ロジックを Postgres 関数に置く

**決定**: 注文作成・ステータス変更・在庫調整を RPC（SECURITY DEFINER 関数）として実装する。

**採らなかった案**

- _ブラウザから複数回クエリを投げる_ — 在庫の引き当ては read-modify-write なので、同時注文で確実に競合する。`supabase-js` にトランザクションを跨ぐ手段はない。
- _API サーバー（Next.js Route Handlers 等）を立てる_ — トランザクションは書けるが、認可の境界が RLS と二重化する。「サーバーを経由しない直接アクセス」を塞ぐ設定も別途必要になる。

**理由**: 不可分に実行すべき処理を1トランザクションに閉じ、行ロックで直列化できる。副次的に、アプリを経由せずに在庫だけ書き換える経路も塞げる。

**代償**: ロジックが SQL に散ることと、テストに DB が必要になること。後者には、**判定ロジックを `packages/core` に純粋関数として切り出す**ことで対処した（DB 関数は実行と強制を担当し、判定規則は TypeScript 側でも検証できる）。

---

## 5. 遷移規則を DB と TypeScript の両方に持つ

**決定**: 注文ステータスの遷移表を、`is_valid_order_transition()`（SQL）と `order-status.ts`（TS）の両方に置く。

**これは重複だが、役割が違う**

|       | 役割                                                 |
| ----- | ---------------------------------------------------- |
| DB 側 | 規則を**守らせる**。UI を通らない更新でも破れない    |
| TS 側 | 規則を**見せる**。押せない遷移のボタンを描かないため |

TS 側を消すと「押せるが失敗するボタン」が出る。DB 側を消すと規則が防御でなくなる。

**ずれのリスクへの対処**: 全 25 通りの組み合わせを明示した表をテストに書き、SQL 側と一字一句対応させた。片方だけを変更すればテストが落ちる。

---

## 6. Next.js ではなく Vite

**決定**: React + TypeScript + Vite。静的ビルドを CDN に配信する。

**理由**: 認証の内側だけで動く管理画面であり、SEO も OGP も公開ページも不要。Next.js の主価値（SSR / ISR / RSC）がほぼ使われない一方、ビルドとデプロイの複雑さは増える。権限の境界を RLS に置く設計上、サーバー層そのものが不要。

**判断が変わる条件**: Phase 3 の外部モール連携を実 API で行う段階で、秘密鍵を持つサーバー側処理が常時必要になった場合。Cloudflare Workers で足りなければ API 層の追加か Next.js への移行を検討する。

---

## 7. UI ライブラリを使わない

**決定**: ボタン・入力・表・モーダルを自前で持つ（`components/ui.tsx`）。

**理由**: 必要な部品が少なく、ライブラリの流儀に合わせるコストの方が大きい。業務システムで重要なのは見た目の凝り方ではなく、表の可読性（桁揃え・行の高さ）と、**読み込み中・空・エラーの3状態を必ず描き分けること**。後者を型のある部品として用意する方が、この規模では効果が大きい。

**判断が変わる条件**: 日付ピッカーや複雑なデータグリッドが必要になったとき。それらは自前で作るべきものではない。

---

## 8. 集計を Phase 1 ではクライアント側で行う

**決定**: ダッシュボードの集計は、商品と直近注文を取得してブラウザ側で計算する。

**理由**: 小規模ショップ（商品数百点・注文数百件/月）の規模では往復1回に収まる。集計ビューやマテリアライズドビューを先に作るのは早すぎる最適化になる。

**判断が変わる条件**: Phase 2 で日別・月別の売上推移を扱う段階。表示のために全件を取得しなければならなくなったら、集計を DB 側のビューに移す。

---

## 9. 型定義を手書きで置いている

**決定**: `packages/core/src/database.types.ts` を、`supabase gen types` の出力と同じ形で手書きする。

**理由**: ローカル Supabase（Docker）を起動していない環境でも型チェックとテストが通るようにするため。CI で DB を立てずに検証できる。

**運用**: スキーマ変更時は `pnpm db:types` で再生成する。生成物と同じ形（Row / Insert / Update / Relationships / Enums / Functions）を保っているので、再生成しても利用側のコードは変わらない。

なお `orders` / `order_items` / `stock_movements` の `Insert` を空にしてあるのは意図的で、直接 INSERT する経路を型の段階で塞いでいる。これらは RPC 経由でのみ作成される。

---

## 10. テストを業務ロジックに絞る

**決定**: `packages/core` の純粋関数のみをテストする。画面のスナップショットや CRUD の往復は書かない。

**理由**: テストの価値は「壊れたときの被害 ÷ 維持コスト」で決まる。在庫の計算やステータス遷移は、間違えると金銭的損失やデータ不整合に直結する一方、規則が安定しているので維持コストが低い。画面のスナップショットは逆で、被害が小さく、変更のたびに壊れる。

**判断が変わる条件**: RPC 関数自体の振る舞い（同時実行時のロック、キャンセルの冪等性）を検証したくなったら、テスト用 DB に対する統合テストを別に追加する。Phase 2 の CSV インポートは変換処理が複雑になるため、そこは純粋関数として切り出したうえでテストを書く。

---

## 11. 集計を DB のビューへ移した（Phase 2）

**決定**: 売上と顧客の集計を `daily_sales` / `monthly_sales` / `product_sales` / `customer_summary` の4本のビューに移す。

**理由**: 判断 8 に書いた「表示のために全件を取得しなければならなくなったとき」に到達した。30日分の棒グラフを描くのに数百件の注文をブラウザへ運ぶ必要はない。

**付随する2つの判断**

- _日付は JST で切る_ — DB のタイムゾーンは UTC。`ordered_at::date` では日本時間 9:00 より前の注文が前日に計上される。営業日で切られていない日別売上に意味は無い。
- _`security_invoker = on` を付ける_ — ビューは既定でビュー所有者の権限で実行され、元テーブルの RLS を迂回する。権限の境界を DB に置く設計上、ビューだけ例外にはできない。

**判断が変わる条件**: 注文が数十万件を超えて、ビューの集計がリクエストごとに走るのが重くなったとき。そのときはマテリアライズドビュー + 定期更新（Cloudflare Workers から呼ぶ）に切り替える。

## 12. CSV 取り込みは「全件成功か、全件中止か」

**決定**: 取り込みは `import_orders` RPC の1トランザクションで行い、1件でも失敗したら何も残さない。

**採らなかった案**

- _有効な行だけ取り込み、失敗した行を報告する_ — 一見親切だが、途中まで取り込まれたファイルを直して再実行したときに何が起きるかを利用者が予測できない。「どこまで入ったか」を利用者が把握し続ける必要が生まれる。

**理由**: 利用者に必要な規則を「CSV を直して丸ごと流し直せばよい」の一文に収めたい。部分適用を許すと、この一文が「ただし取り込み済みの行は除く、ただし在庫は既に引かれている…」と伸びていく。

**代償**: 1行のミスで全件が止まる。これは取り込み前の検証（`parseOrderCsvRows`）で行番号付きの一覧を出すことで緩和している。

---

## 13. 取り込みの重複はスキップし、エラーにしない

**決定**: `orders.external_order_id` に一意制約を張り、取り込み済みの注文は飛ばして件数だけ返す。

**理由**: 同じファイルを二度流すのは事故ではなく、よくある操作（途中で失敗した、取り込めたか不安でもう一度流す）。エラーで止めると、利用者は「何が入って何が入っていないか」を自分で調べることになる。飛ばして件数を返せば、取り込みは何度実行しても同じ結果になる。

これは Phase 1 の `orders.stock_committed`（キャンセルの二重戻し防止）と同じ考え方で、**外部から繰り返し呼ばれうる操作は冪等にする**という方針を取り込みにも適用したもの。

---

## 14. 取り込んだ注文の単価は CSV の値を優先する

**決定**: `create_order` の明細に単価を明示できるようにし、取り込み時は CSV の単価を使う。指定が無ければ従来どおり商品マスタの現在価格をスナップショットする。

**理由**: 取り込むのは「実際にその価格で売れた」履歴。マスタの現在価格で上書きすると、値引きやキャンペーン販売の実績が消え、売上集計が実際の入金と食い違う。

**なぜ取り込み専用の経路を作らなかったか**: 明細を直接 INSERT する別経路を作れば単価は自由に置けるが、在庫の引き当てを通らない経路が生まれる。「台帳が在庫の真実である」前提を守るため、取り込みも `create_order` を通す。UI からは単価を渡さない（価格の手入力欄を設けない）。

---

## 15. グラフをライブラリではなく SVG で描く

**決定**: 売上推移の棒グラフを、依存を足さずインライン SVG で描く。

**理由**: 必要なのは1系列の棒グラフだけで、グラフライブラリの多機能はほぼ使わない。数十 KB を足して得られるのが目盛りの自動計算程度なら、その計算（`niceAxisMax`）を `packages/core` に置いてテストする方が確かめやすい。判断 7（UI ライブラリを使わない）と同じ基準。

グラフ自体の規則もいくつか決めている。系列が1本なので単色で凡例は出さない。縦軸は1本だけにする（売上と注文数を重ねると尺度の違うものを並べて読み違える）。時間軸には縦の目盛り線を引かない。売れなかった日も棒の位置を空けて残す（詰めると「毎日売れている」ように見える）。

**判断が変わる条件**: 複数系列の比較や、ズーム・ブラシ操作が必要になったとき。そこからは自前で持つ理由がない。

---

## 16. 権限の線引きは「金額」と「一括操作」で引く（Phase 3）

**決定**: 商品マスタの登録・編集と、CSV / チャネルの一括取り込み、メンバー管理・店舗設定を owner に限る。注文処理・在庫調整・顧客登録は staff も行える。viewer は何も書けない。

**採らなかった案**

- _画面単位で権限を割る（「商品ページは owner のみ」）_ — 同じページの中で「閲覧はできるが更新はできない」という、実際に必要な状態を表せない。権限は操作の単位で定義した。
- _staff にも商品編集を許す_ — 価格と原価は売上・粗利の計算根拠そのもの。日々の出荷業務とは影響範囲が違う。

**理由**: 「間違えたときにどこまで戻すのが大変か」で線を引いた。出荷ステータスの取り違えは1件を直せば済むが、価格の書き換えは以後の売上集計に効き、一括取り込みは1回で数十件の注文と在庫移動を作る。

---

## 17. 権限は DB に置き、画面側は「見せる」だけ（Phase 3）

**決定**: RLS ポリシーと `assert_write_access()` / `assert_owner_access()` が実際の制限。`packages/core/src/permissions.ts` はボタンの出し分けにのみ使う。

これは Phase 1 の注文ステータス遷移（判断 5）と同じ構造で、本システムでは3度目になる。守らせる側と見せる側を分け、両者のずれは網羅テストで検知する、という方針を一貫させている。

**この区別を保つための制約**: 画面側で権限を判定した結果をサーバーに送らない（「権限があります」と申告しない）。送った時点で、画面側の判定が防御の一部になってしまう。

---

## 18. 最後の管理者は降格できない（Phase 3）

**決定**: `set_member_role()` が、owner が1人しかいないときのその owner の降格を拒否する。

**理由**: 許すと誰も権限を変更できない状態になり、DB に直接触れる人以外は復旧できない。権限管理を入れるときに最初に塞ぐべき穴で、後から気付くと実際に閉め出された利用者が出てからになる。

**関連して気付いたこと**: RLS で弾かれた UPDATE は、エラーではなく「0 行更新」として返る。そのため書き込み系のクエリには `.select().single()` を付けている。付けないと、権限が無いのに「保存しました」と表示してしまう。RLS を後から入れるときに見落としやすい挙動。

---

## 19. create_order を「公開ラッパー + 内部実装」に分けた（Phase 3）

**決定**: 業務ロジックを `create_order_internal` に移し、公開側の `create_order` は権限を確認して委譲するだけにした。

**理由**: Phase 2 で単価の指定を足すために、Phase 3 で権限確認を足すために、と 90 行の関数をマイグレーションのたびに複製し続けることになっていた。以降、業務ロジックの変更は internal 側だけ、権限の変更は公開側だけを触ればよい。

`import_orders` は自分で owner を確認したうえで internal を呼ぶ（同じ確認を二度しない）。

---

## 20. PDF 生成ライブラリではなくブラウザ印刷（Phase 3）

**決定**: 納品書と出荷ラベルを HTML + `@media print` で作り、ブラウザの印刷機能に任せる。

**採らなかった案**

- _jsPDF / pdf-lib でクライアント生成_ — 日本語を出すには数MBのフォントをバンドルに埋め込むことになる。得られるのは出力の厳密な制御だが、現時点の帳票要件はそこまで厳密ではない。
- _Worker 側で生成_ — 同じフォント問題に加えて、帳票のためだけにサーバー処理が増える。

**理由**: 日本語フォントが要らないこと、レイアウトを既存と同じ技術（HTML / CSS）で書けること、そして宅配便の伝票は実際に紙で刷るので PDF を経由しない方が手順が短いこと。「PDF として保存」も同じ印刷ダイアログから選べる。

**代償**: 余白やヘッダー・フッターがブラウザ依存になる。

**判断が変わる条件**: 角印の位置指定や、決まった様式への差し込み印刷が必要になったとき。

---

## 21. モール連携のモックは「境界」を本番と同じにする（Phase 3）

**決定**: モックが作るのは「外部から受け取った注文データ」（`ImportOrder[]`）までとし、そこから先は CSV 取り込みと同じ `import_orders` を通す。

**採らなかった案**

- _画面表示用のダミー注文を直接 INSERT する_ — 見た目は同じものが作れるが、在庫の引き当ても冪等性も通らない。実 API に差し替えるときに、取り込み処理をまるごと書くことになる。

**理由**: 連携で実際に難しいのは API の呼び出し方ではなく、**同じ注文を何度も受け取っても二重登録しないこと**。ポーリングでは同じ注文が繰り返し届く。そこを本番と同じ形で作っておけば、実 API 連携で書き換えるのはデータの取得元だけで済む。

そのため生成は決定的にしてある。同じ日に2回同期すると、同じ `external_order_id` が生成され、2回目は「0 件取り込み / 3 件スキップ」になる。この挙動はテストでも固定している。

---

## 22. 販売ペースは在庫台帳ではなく注文日で測る（Phase 4）

**決定**: `stock_velocity()` の販売数を `orders.ordered_at` から数える。`stock_movements.created_at` は使わない。

**理由**: 台帳の時刻は在庫が動いた瞬間であって、売れた瞬間ではない。CSV やモールから過去の注文を取り込むと、在庫移動は取り込んだ瞬間に記録される。台帳基準で数えると、半年前の注文が「今日まとめて売れた」ことになり、販売ペースが跳ね上がって発注推奨が壊れる。

**気付いた経緯**: 最初は台帳基準で実装し、動かしてみたところ全商品の観測開始日がシード投入日（＝同じ日）になっていた。データの入れ方の問題に見えたが、Phase 2 の取り込み機能を通した本番でも同じことが起きると分かった。

Phase 1 で `ordered_at`（実際の注文日時）と `created_at`（レコード作成日時）を別の列にしておいた判断が、ここで効いている。

---

## 23. 予測は「検算できる式」に留める（Phase 4）

**決定**: 単純な割り算（期間内の販売数 ÷ 観測日数）だけを使う。移動平均・季節性・安全在庫係数は入れない。

**採らなかった案**

- _移動平均や指数平滑_ — 小規模ECの日次データは 0 の日が多く、平滑化しても精度は目に見えて上がらない。
- _季節性の考慮_ — 1年分のデータが貯まるまで意味がなく、貯まった頃には商品構成が変わっている。

**理由**: 「30日で60個 → 1日2個 → 在庫20個なら10日」を運営者が暗算で確かめられること。説明できない予測は、一度外れると使われなくなる。精度を上げる努力より、外れ方が予想できることの方がこの規模では価値がある。

**この決定から派生した実装上の制約**: 画面に出す観測日数と、計算に使う日数を一致させる。端数を残して計算し表示だけ切り下げると「17個 ÷ 10日」の表示に対して 1.6/日 と出て、検算が合わなくなる。実際に最初の実装がこうなっており、画面で確認して気付いた。

---

## 24. 予測しない場合を明示する（Phase 4）

**決定**: 観測期間が1週間に満たない商品と、期間内の販売が 0 の商品は予測を返さない（null）。

**採らなかった案**

- _販売 0 を「無限日もつ」として扱う_ — 「まだ売れていない」新商品と「もう売れない」死に筋を同じに扱うことになる。このデータだけでは区別できない。
- _数日の実績でも予測を出す_ — たまたま売れた日が1日あっただけで、ペースが数倍に振れる。

**理由**: 予測できないことを示すのは、誤った予測を出すより情報量が多い。運営者は「判断材料が無い」と分かれば自分の勘で補える。

あわせて、実績の量と期間から信頼度（実績十分 / 参考値 / ばらつき大 / 実績不足）を返し、数字だけが独り歩きしないようにしている。

## 25. 通知は「送る前に記録する」（Phase 4）

**決定**: `notifications` テーブルに dedupe_key の一意制約を張り、`insert ... on conflict do nothing` の結果で送信可否を決める。送信より先に記録する。

**理由**: Cron は同じ時刻に二度走ることがあり、手動実行や再デプロイでも重複しうる。同じ在庫切れを1日に何度も Slack に流すと、運営者は通知そのものを見なくなる。

**送信と記録の順序**: 先に送ると、送信成功後に記録へ失敗したとき二重送信になる。先に記録すると送信失敗時に通知が欠ける。在庫アラートは翌日も届き、大口注文は画面でも確認できるので、欠けるより二重に鳴る方が実害が大きいと判断した。

**判定と記録を分けない**: 「送ったか確認する → 送る → 記録する」と3段に分けると、確認と記録の隙間で複数の Worker が同時に「まだ送っていない」と判断しうる。一意制約に判定させることで、この隙間が構造上なくなる。

これは Phase 2 の CSV 取り込み（`external_order_id` の一意制約）、Phase 1 の在庫引き当て（`stock_committed`）と同じ考え方で、本システムでは3度目になる。**外部から繰り返し呼ばれうる操作は冪等にする**という方針を一貫させている。

## 26. 大口注文の検出は「時刻の差分」ではなく「注文ごとの記録」（Phase 4）

**決定**: 前回実行時刻を保存せず、注文 ID を dedupe_key にする。

**採らなかった案**

- _前回実行時刻を保存し、それ以降の注文を通知する_ — 実行が飛べば取りこぼし、二度走れば重複する。「いつ実行したか」という状態を正しく保つ責任が増える。

**理由**: 注文ごとの記録なら、いつ何度走っても結果が同じになる。定期処理が数日止まっていても、再開時に取りこぼしなく通知できる。

対象を直近2日の注文に絞っているのは、初回実行で過去の全注文が一斉に流れるのを防ぐため。
